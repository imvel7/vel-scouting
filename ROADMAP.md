# Vel Scouting — Proje Yol Haritası v1.0

**Tarih:** 10 Kasım 2026  
**Durum:** Metodoloji temeli oluşturuldu. Güncel ürün yönü: özel scouting video/maç kaynak sistemi ile kamuya açık raporlama alanını kesin biçimde ayırmak.

## 1. Proje hedefi ve ürün ilkeleri

Vel Scouting; farklı yaş ve seviyelerdeki futbolcuları kapsayan, özellikle genç yeteneklere odaklanan bağımsız bir futbolcu değerlendirme platformudur.

İlk ürünün amacı futbolcuyu yalnızca “potansiyelli” diye etiketlemek değil; önce bugünkü oyununu, oynadığı rolü ve gözlemlenebilir performansını kanıta dayalı biçimde tanımlamaktır. Potansiyel ve transfer uygunluğu daha sonra, ayrı değerlendirme katmanları olarak ele alınacaktır.

Temel ilkeler:
- Gözlem ve kanıt, kanaatin önünde gelir.
- Maç bağlamı, oyuncunun rolü ve takımın oyun yapısı puanlamaya dâhil edilir.
- Mevcut performans, potansiyel ve transfer uygunluğu birbirine karıştırılmaz.
- Yetersiz video veya veri, düşük puan olarak yorumlanmaz.
- Metodoloji sürümü ve rapor geçmişi korunur.
- Genç oyuncuların mahremiyeti ve güvenliği ürün tasarımının başından itibaren gözetilir.
- Video içerikleri izinsiz kopyalanmaz veya yeniden yayımlanmaz; kaynak ve kullanım hakları kaydedilir.

## 2. Şu ana kadar tamamlananlar

- Ortak değerlendirme çerçevesi v1.0 oluşturuldu.
- Stoper, bek/kanat bek, ön libero/merkez orta saha, hücumcu orta saha/10 numara, kanat, santrfor ve kaleci metodoloji dokümanları hazırlandı.
- Pozisyon ve rol sınırları dokümante edildi.
- İlk metodoloji kalite denetimi tamamlandı: ağırlık toplamları, alan hesapları ve rol ayrımları kontrol edildi.
- Stoper için 37 alt kriterin tamamına gözlenebilir davranış tanımları ve altı puan bandı içeren puanlama çıpaları v1.0 hazırlandı.
- Kalite denetimi raporunda puanlama çıpalarının yalnızca stoper için tamamlandığı, diğer altı pozisyon grubunun ve pilot kalibrasyonun beklediği açıkça kaydedildi.

**Önemli:** Bunlar dokümantasyon ve mantıksal tutarlılık kontrolleridir. Henüz gerçek maç üzerinde pilot yapılmış veya iki değerlendirici arasında kalibrasyon kanıtlanmış değildir.

## 3. Aşamalı devam planı

### Aşama 1 — Stoper pilotunu hazırlama

**Durum: Şablon v1.0 hazırlandı; gerçek maç üzerinde iş akışı testi bekliyor.**

Çıktılar:
- Tek tip maç ve oyuncu katılım bilgi formu.

Kontroller:

**Çıkış ölçütü:** Şablon gerçek bir maç üzerinde baştan sona doldurulabiliyor; gözlem ile yorum ayrılıyor ve eksik kanıt yanlışlıkla sıfır puana dönüşmüyor.

**Çıkış ölçütü:** Uyuşmazlıklar açıklanmış, çıpalar gerekli yerlerde düzeltilmiş ve stoper rubriğinin hangi koşullarda güvenilir kullanılabileceği belgelenmiş olur.

Mevcut Supabase yapısında maç, oyuncu-maç bağlantısı, video, gözlem, scout raporu ve rapor sürümü tabloları bulunuyor. Ancak mevcut gözlem kaydı ve rapor formu kriter bazlı puanlamayı, değerlendirici ayrımını ve kalibrasyon geçmişini tek başına karşılamıyor.

- Rubrik/metodoloji sürümü.
- Bağımsız değerlendirmelerin karşılaştırılması.
- Hesaplanan alan puanları, kriter kapsamı ve rapor anlık görüntüsü.

**Kontrol:** Gerçek Supabase şeması yeniden doğrulanmadan SQL veya yönetim paneli alanları varsayımla değiştirilmez.

**Çıkış ölçütü:** Gözlemden rapora kadar tüm puanların kaynağı izlenebilir; eski raporlar yeni metodoloji güncellemesiyle sessizce değişmez.

## 7. Continuation audit — 11 November 2026

### Confirmed live database access posture

A read-only audit of the live Supabase project confirmed:
- All 19 public tables have RLS enabled.
- Anonymous table-level SELECT is granted only for `players`, `clubs`, and `scout_reports`; their policies expose published player profiles, clubs linked to published players, and published reports belonging to published players.
- The remaining 16 tables do not grant anonymous SELECT. The `private` schema does not grant USAGE to `anon`.
- `private.is_vel_staff()` and `private.is_vel_admin()` are SECURITY DEFINER helpers with an empty search_path and EXECUTE granted only to `authenticated` (plus the database owner). They derive authorization from `auth.uid()` and `public.user_roles`.
- `create_scout_report_bundle()` and `create_multi_match_scout_report_bundle()` are SECURITY INVOKER functions with an empty search_path; EXECUTE is granted to `authenticated`, not `anon`.

These are SQL/catalog-level checks. They do not replace a browser Data API test with real anonymous, staff, and non-staff sessions.

### Admin browser diagnostics expanded

On 11 November 2026, `admin.html` was updated so its read-only anonymous-access diagnostic checks all 16 private tables, rather than the previous subset of 10. The change was committed to `main`:
- Commit: `6b8ba3a11602e4f6e1125d37cf4751897063ade0`
- The updated file was fetched again from GitHub and the 16-table list was verified.

**Still pending:** run the diagnostic from the deployed GitHub Pages admin panel using an authorized staff account. A separate authenticated non-staff account is also needed to verify the staff-only RLS boundary through the actual Data API. The assistant has not accessed the user's browser session and has not run these interactive checks.

### Migration source-tracking gap

The live database migration ledger contains eight applied migrations, but the current `main` branch tracks only two SQL files under `supabase/migrations`:
- `20261110172515_tighten_vel_rls_function_privileges.sql`
- `20261110174605_create_vel_scouting_sessions_and_rubrics.sql`

The six later migration versions present in the live ledger do not have corresponding SQL files in the current repository tree:
- `20261111085851_create_atomic_scout_report_bundle`
- `20261111104333_create_multi_match_scout_report_rpc`
- `20261111105655_use_existing_secure_scout_report_bundle`
- `20261111105858_fix_report_bundle_uuid_aggregate`
- `20261111110233_add_multi_match_report_guard`
- `20261111110636_enforce_multi_match_rubric_methodology`

Do not invent historical SQL or apply additional DDL until the missing source history is recovered or a reviewed, explicitly labelled live-state recovery baseline is prepared. The live RPC definitions have been inspected, but that is not a substitute for the exact six historical migration scripts.

### Admin report workflow integration

The admin report workflow was updated on 11 November 2026 and now uses the existing secure report-bundle RPCs instead of inserting into `scout_reports` and `report_versions` separately:
- One-match / same-match session bundles call `create_scout_report_bundle()`.
- Multi-match bundles call `create_multi_match_scout_report_bundle()`; the UI and database both enforce the completed/locked session requirement and the multi-match minimum.
- Methodology version is read from the selected `rubric_versions` row; the hardcoded `0.8` value was removed.
- The report snapshot captures the selected player, rubric, session/match context, criterion scores, timestamped observations, and linked video-source metadata.
- Evidence grade and general rating are calculated server-side; they are no longer manually entered in the report form.

Static verification passed: the fetched module script compiles, duplicate HTML IDs were not found, and the old direct inserts are absent. A real RPC write was intentionally not run because the live database currently contains zero scouting sessions. Multi-match report creation remains blocked until the admin workflow can move sessions through a reviewed completion lifecycle.

### Latest advisor findings

- Security: leaked-password protection is disabled; this remains a plan limitation already documented for the current Free tier.
- Performance: 23 foreign keys are reported without covering indexes; four tables have multiple permissive SELECT policies; 12 indexes are currently unused. Review these against actual query patterns before making index or policy changes.
- Health: no advisor findings were returned in this check.
